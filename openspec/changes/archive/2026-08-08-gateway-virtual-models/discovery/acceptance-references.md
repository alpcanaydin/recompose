# Acceptance references for `gateway-virtual-models`

Scope note and gap, stated up front: I could not open `openspec/changes/gateway-virtual-models/` (no `proposal.md` at that path on this branch), and this arm has no Grep/Glob, so nothing from `packages/contracts` or the engine was read. Every repository claim below comes from four files I did read: `README.md`, `openspec/specs/gateways/spec.md`, `docs/adr/README.md`, `docs/adr/0059-the-slug-rule-tightens-to-a-device-safe-identifier.md`. Treat the criteria as candidates to reconcile against the contracts source.

## 1. The finding that outranks everything else

Anthropic publishes a written contract for gateways, and it constrains virtual-model naming directly. From the [gateway protocol reference](https://code.claude.com/docs/en/llm-gateway-protocol) (fetched 2026-08-04; text references Claude Code v2.1.219, so it is current):

- Model discovery: "When `ANTHROPIC_BASE_URL` points at a gateway that exposes the Anthropic Messages format, Claude Code can query the gateway's `/v1/models` endpoint at startup and add the returned models to the `/model` picker." It is **off by default**, enabled per developer with `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`, and needs Claude Code v2.1.129+.
- The request is "`GET /v1/models?limit=1000` with a 3-second timeout, and any redirect is treated as failure". A slow or redirecting endpoint "fails discovery silently".
- Discovery sends exactly one credential header: `ANTHROPIC_AUTH_TOKEN` as a bearer token when set, otherwise the resolved API key in `x-api-key`. Inference requests send both. "A gateway that authenticates `/v1/models` must accept `x-api-key` for helper deployments."
- The killer clause: "Claude Code reads `id` and the optional `display_name` from each entry in the response's `data` array, and **ignores entries whose `id` doesn't begin with `claude` or `anthropic`**." The doc's own remedy: "If your gateway serves Claude models under aliases that don't match the discovery filter, developers can add those aliases manually with the model configuration variables."

`README.md` sells virtual models with the examples `fast` and `smart`, and the canvas diagram uses `virtual model "fast"`. Under this filter, `fast` and `smart` never reach the Claude Code picker. That is a product-visible acceptance gap, not a bug in either side.

## 2. What Claude Code actually sends, which decides resolution rules

- Behind a custom base URL, model strings are unvalidated and arbitrary: "your provider or gateway defines the model names, so Claude Code passes any string through without checking it" ([model configuration](https://code.claude.com/docs/en/model-config), fetched 2026-08-04). So a virtual model name may be any string the client can type, and the gateway is the only validator.
- Aliases the client may resolve or pass along include `default`, `best`, `fable`, `sonnet`, `opus`, `haiku`, `sonnet[1m]`, `opus[1m]`, `opusplan`. The same page documents `sonnet[1m]` as behaving specially "behind an [LLM gateway], selects the 1M window for Sonnet 5", which is vendor confirmation that bracketed variants are part of gateway traffic. The exact on-the-wire spelling of the suffix is only attested by third-party write-ups, so treat "strip `[1m]`" as a hypothesis to verify with a capture, not a fact.
- Endpoints in the Anthropic Messages row: "`/v1/messages`, `/v1/messages/count_tokens` (optional)". Also: "Inference requests post to `/v1/messages?beta=true`, so **match on the path, not the full URL**." Startup traffic includes a `HEAD /` probe that a gateway "can reject without breaking anything".
- Streaming is mandatory: "a gateway that buffers complete responses before relaying them stalls the client."
- Errors must pass through untouched: "The retry logic matches on the upstream's error wording, so forward error response bodies unmodified. A gateway that wraps upstream errors in its own envelope breaks the recovery path even when it preserves the status code." This is a hard constraint on any per-virtual-model error decoration.
- The virtual-model-specific trap: adaptive reasoning has "No beta header. Claude Code sends `thinking: {"type": "adaptive"}` for Claude 4.6 and later, and **treats model names it doesn't recognize, such as gateway aliases, as current models that receive the field**", with the symptom "`400` naming the `thinking` field or the `adaptive` tag when the upstream model build doesn't accept it." Naming a virtual model `fast` therefore opts every request into adaptive thinking regardless of what sits behind it. The same page notes `ANTHROPIC_DEFAULT_*_MODEL_SUPPORTED_CAPABILITIES` "have no effect behind an `ANTHROPIC_BASE_URL` gateway", so the client cannot be told otherwise.

## 3. Broken expectations from the field

Unknown-model traffic a proxy did not plan for:

- Claude Code's internal Haiku calls traverse the same base URL, and subagents have been reported sending the literal string `haiku`, producing `404 {"type":"error","error":{"type":"not_found_error","message":"model: haiku"}}` ([claude-code#16115](https://github.com/anthropics/claude-code/issues/16115)).
- A reporter blamed a gateway for disabled ToolSearch because a capability check resolved against `claude-haiku-4-5-20251001` rather than the session model, while stating "The gateway is a dumb pass-through" ([claude-code#32378](https://github.com/anthropics/claude-code/issues/32378), filed 2026-03-09, closed as duplicate, no maintainer diagnosis). Cite it as a user expectation, not a confirmed mechanism.

Token counting, where vendor doc and field reports disagree:

- Vendor says optional with graceful degradation: absent, "Claude Code falls back to estimating context usage locally" ([protocol reference](https://code.claude.com/docs/en/llm-gateway-protocol)).
- Field reports say a missing route is worse than that: cc-switch registered only exact `/v1/messages`, so `count_tokens` 404s and "auto context compression fails" ([cc-switch#3260](https://github.com/farion1231/cc-switch/issues/3260)); LiteLLM logged `count_tokens?beta=true ... 404` from `claude-cli` before implementing it ([litellm#13252](https://github.com/BerriAI/litellm/issues/13252), now [documented](https://docs.litellm.ai/docs/anthropic_count_tokens) returning `{"input_tokens": N}`); Ollama became unresponsive after repeated 404s on `/v1/messages/count_tokens?beta=true` ([ollama#13949](https://github.com/ollama/ollama/issues/13949)). Resolution: the doc is authoritative on optionality, the reports are authoritative on the cost of a sloppy 404. Serve the route for virtual models, or return a well-formed Anthropic error body fast.

Alias-versus-routing bugs, the prior art most worth copying away from:

- An aliased model does not inherit the underlying group's fallbacks: config `model_group_alias = {"alias-model": "real-model"}` with `fallbacks = [{"real-model": ["fallback-model"]}]` fails with "No fallback model group found for original model_group" ([litellm#10317](https://github.com/BerriAI/litellm/issues/10317), opened 2025-04-25, closed as not planned). Same class in [#15493](https://github.com/BerriAI/litellm/issues/15493) (Oct 2025, closed not planned) and [#27473](https://github.com/BerriAI/litellm/issues/27473), where the pre-alias name leaks into the fallback lookup. Users' workaround is to key fallbacks on both names.
- Aliases defined in config were ignored once the database became the source of truth ([litellm#15020](https://github.com/BerriAI/litellm/issues/15020)): two stores, one wins silently.
- A config containing `router_settings.model_group_alias` crashed the models page ([litellm PR#15308](https://github.com/BerriAI/litellm/pull/15308)): the management UI must survive alias data it does not fully understand.
- Note the deliberate divergence: in LiteLLM two deployments sharing `model_name` form a load-balanced group ([routing docs](https://docs.litellm.ai/docs/routing)). recompose puts pooling in routers, so a virtual model name must be unique per gateway. Say so explicitly, because the ecosystem's default reading of a duplicate name is "pool", not "conflict".

OpenAI-dialect clients:

- Clients populate their picker from `GET /v1/models`, whose entries are `{id, object: "model", created, owned_by}` inside `{"object":"list","data":[...]}` ([OpenAI list models reference](https://developers.openai.com/api/reference/resources/models/methods/list)). A malformed or empty `data` array yields an empty dropdown.
- IDs must match "exactly, including casing, version suffixes, and any namespace prefixes"; Cursor has been observed rejecting a provider's IDs with `Model name is not valid: ''` ([Cursor forum report](https://forum.cursor.com/t/cursor-custom-openai-provider-rejects-valid-gloo-model-ids-as-model-name-is-not-valid/158958)), and Cline's docs point "Model Not Found" at an ID that is not valid at that base URL ([Cline OpenAI-compatible docs](https://docs.cline.bot/provider-config/openai-compatible)).
- Premise check that affects this feature's reach: Codex CLI is named as a client in `README.md`, but the official Codex configuration reference states that for `model_providers.<id>.wire_api`, "`responses` is the only supported value, and it is the default when omitted" ([Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), fetched 2026-08-04; the [advanced config page](https://learn.chatgpt.com/docs/config-file/config-advanced) shows only `wire_api = "responses"` in every example and never documents a `chat` value). A gateway that serves only `/v1/chat/completions` is therefore not reachable from current Codex CLI. Secondary write-ups date the removal of `chat` to February 2026 and report a startup refusal; I did not find that in first-party text, so treat the date and the error string as unverified. Either way this is a scope question for the proposal, not something virtual models fix.

## 4. Candidate acceptance criteria, in the house spec voice

Naming and identity

1. A virtual model name MUST be unique within its gateway, compared case-insensitively, because clients must match the id exactly including casing.
2. The name MUST be usable as a path segment and as a JSON string: no whitespace, no `/`, bounded length. `docs/adr/0059-the-slug-rule-tightens-to-a-device-safe-identifier.md` already sets 63 characters as the house bound for a device-safe identifier, and ADR-0061 already establishes deriving an identifier from a display name; reuse both rather than inventing a second grammar.
3. The creation surface MUST tell a person, at naming time, that a name not beginning with `claude` or `anthropic` will not appear in the Claude Code picker, and MUST name the manual route (`ANTHROPIC_MODEL` or the `ANTHROPIC_DEFAULT_*_MODEL` variables).
4. Renaming a virtual model MUST take effect on the serving path without a second source of truth outranking the stored document (the `litellm#15020` failure), and the surface MUST state whether a restart is needed.

Resolution and routing 5. A request naming a virtual model MUST resolve to that model's router chain, and every failover decision MUST be keyed on the resolved chain, never on the name the client sent (`litellm#10317`, `#15493`, `#27473`). 6. A request naming an unknown model MUST fail with the dialect's own error shape (`404` with `error.type = "not_found_error"` on `/v1/messages`; the OpenAI error envelope on `/v1/chat/completions`) and MUST NOT hang or return an empty body. 7. Route matching MUST be on path only, so `/v1/messages?beta=true` and `/v1/messages/count_tokens?beta=true` both resolve. 8. `HEAD /` MUST be answered or rejected cleanly without touching virtual-model resolution.

Discovery and listing 9. `GET /v1/models` MUST answer at the gateway base URL with no redirect, within the client's 3-second budget, listing every virtual model of that gateway and nothing else. The Anthropic-dialect response MUST carry `data[].id` plus `display_name`; the OpenAI-dialect response MUST carry `{"object":"list","data":[{id, object:"model", created, owned_by}]}`. 10. `GET /v1/models` MUST accept `x-api-key` as well as bearer `Authorization`, since discovery sends only one of them. 11. A gateway whose virtual model points at a missing or deleted target MUST still list, load, and render, extending "A gateway exists before its first model" in `openspec/specs/gateways/spec.md` (the `litellm PR#15308` crash class).

Pass-through fidelity 12. Upstream error bodies MUST reach the client unmodified, and per-virtual-model context MUST NOT be added to the envelope. 13. `anthropic-beta` and `anthropic-version` MUST be forwarded verbatim, as open lists, with no allowlist of observed values. 14. Responses MUST stream as they arrive; no buffering of a complete response. 15. A virtual model MUST resolve on `/v1/messages/count_tokens` the same way it resolves on `/v1/messages`.

## 5. Recommendation

Ship virtual models with a two-part identity: a free display name plus a derived, bounded, lowercase identifier reusing the ADR-0059/0061 machinery, and default the identifier toward the discovery filter (for example prefix Claude-facing virtual models so they begin with `claude-`) while allowing an arbitrary name with an inline warning about the picker consequence. Key all routing on the resolved chain from the first commit; the LiteLLM alias/fallback bug survived four issue reports across a year and two of them closed unresolved, which is what retrofitting looks like. Serve `/v1/models` and `count_tokens` for virtual models in the same change, because both are cheap now and both are documented client expectations. Leave the Codex `/v1/responses` question to its own change, but record it: as of the current Codex reference, the OpenAI-dialect half of `README.md`'s promise does not reach Codex CLI.

Weakest evidence, flagged: the `[1m]` on-the-wire spelling, the Claude Code capability-inference-by-substring claim, and the February 2026 removal of `wire_api = "chat"` are all secondary or user-reported. Each needs a capture or a first-party line before it becomes a criterion.
