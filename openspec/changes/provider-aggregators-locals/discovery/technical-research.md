## Research brief: provider aggregators and local runtimes

**Scope note and honesty about the evidence.** `openspec/changes/provider-aggregators-locals/` does not exist in this worktree yet (both `proposal.md` and `tasks.md` returned "file does not exist"), so I scoped the question from `README.md`, which names the roadmap as "the rest of the key providers and local runtimes (Ollama, LM Studio)", plus the two ADRs that constrain the design: `docs/adr/0069-subscriptions-delegate-to-the-providers-tool.md` and `docs/adr/0070-key-checks-live-in-the-engine-child.md`. Grep and Glob were not available in this session, so I could not enumerate `packages/engine/src/provider/` or find the living providers spec (`openspec/specs/providers/spec.md`, `openspec/AGENTS.md`, and `openspec/project.md` all missed). Every repository claim below is either from a file I read or quoted from an ADR that names the path itself. Treat the repository-shape claims as needing one confirmation pass by whoever holds Grep.

### 1. The de facto standard is now two skins, not one

OpenAI-compatible chat completions is still the lingua franca, but a second dialect has arrived on both sides of this feature:

- **Aggregator side**: OpenRouter documents an Anthropic Messages-format endpoint ("Anthropic Skin") that Claude Code speaks natively, with thinking blocks, native tool use, streaming, and multi-turn context ([OpenRouter Anthropic messages reference](https://openrouter.ai/docs/api/api-reference/anthropic-messages/create-messages), [Claude Code tutorial](https://openrouter.ai/blog/tutorials/claude-code-openrouter/); no publication date on either page). Its Agent SDK guide has you set `ANTHROPIC_BASE_URL=https://openrouter.ai/api` ([guide](https://openrouter.ai/docs/guides/community/anthropic-agent-sdk)).
- **Local side**: LM Studio serves an Anthropic-compatible `POST /v1/messages` with SSE `message_start` / `content_block_delta` / `message_stop` and tool use, introduced in 0.4.1 ([LM Studio Anthropic compatibility](https://lmstudio.ai/docs/developer/anthropic-compat/messages), [Claude Code post](https://lmstudio.ai/blog/claudecode)).

**Implication for recompose.** A target can be Anthropic-native, OpenAI-only, or both. The gateway's dialect translation should be a property of the target, not of the provider family, otherwise you translate Anthropic → OpenAI → Anthropic for an OpenRouter or LM Studio target that would have taken the original bytes. Do not assume either direction: Ollama's OpenAI layer is explicitly labelled "experimental and subject to major adjustments including breaking changes" and drops `tool_choice`, `logit_bias`, `user`, `n`, image URLs, and streaming tool calls ([Ollama OpenAI compatibility](https://ollama.readthedocs.io/en/openai/)).

### 2. The key-check probe from ADR 0070 needs a per-provider base URL and, for OpenRouter, a better endpoint

ADR 0070 fixed the probe as `GET /v1/models` with the vendor's own header. That generalises, with three caveats the vendor docs make explicit:

- **The base path is not `/v1` everywhere.** Groq is `https://api.groq.com/openai/v1/models` with `Authorization: Bearer` ([Groq models docs](https://console.groq.com/docs/models), [OpenAI compatibility](https://console.groq.com/docs/openai)). Gemini's OpenAI skin is `https://generativelanguage.googleapis.com/v1beta/openai/models`, also Bearer ([Gemini OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai)). OpenRouter is `https://openrouter.ai/api/v1` ([authentication](https://openrouter.ai/docs/api_reference/authentication)). A probe that concatenates `/v1/models` onto a host will be wrong for two of the three. The base URL belongs in the provider descriptor, string-joined once.
- **OpenRouter has a credential-scoped probe that beats a model list.** `GET https://openrouter.ai/api/v1/key` with the Bearer key returns `label`, `limit`, `limit_remaining`, `limit_reset`, `usage` (plus daily/weekly/monthly), `byok_usage`, and `is_free_tier`; the same page documents 402 for exhausted credits and 429 with `X-RateLimit-Limit` / `-Remaining` / `-Reset` and sometimes `Retry-After` ([OpenRouter limits](https://openrouter.ai/docs/api-reference/limits)). Those map cleanly onto the typed-failure states `.claude/rules/clean-code.md` asks for (rate limit, auth expired, credit exhausted) and give the account row a balance to display without a second call.
- **A models list can answer about the service rather than about the key.** OpenRouter's own OpenAPI-derived reference marks `GET /models` as covered by the global bearer security scheme ([list models](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties)), yet community tooling routinely reads that catalogue without a key, and I could not resolve the contradiction from the docs alone. Check `https://openrouter.ai/openapi.yaml` before relying on a 401 from `/models` as proof a key is bad; `/api/v1/key` has no such ambiguity because it is defined only in terms of the key. Gemini's forum has a matching report of `/v1beta/openai/models` returning 401 while chat completions with the same key succeeded ([Google AI forum, Dec 2024](https://discuss.ai.google.dev/t/openai-list-models-returns-http-401/52510)), which is the same class of hazard in the other direction.

### 3. Local runtimes invert the verdict: reachability, not validity

- **Ollama** ignores the API key entirely ("required but ignored", `api_key='ollama'`) ([Ollama OpenAI compatibility](https://ollama.readthedocs.io/en/openai/)), binds `127.0.0.1:11434` by default, changes that only through `OLLAMA_HOST`, and allows cross-origin from loopback with `OLLAMA_ORIGINS` for more ([Ollama FAQ](https://docs.ollama.com/faq)). It ships no authentication of its own, so any bind past loopback is a deliberate exposure.
- **LM Studio** has authentication **off by default**; you toggle "Require Authentication" in Developers Page > Server Settings, mint named tokens shown once, and then send `Authorization: Bearer` (the Anthropic endpoint also accepts `x-api-key`). Requires LM Studio 0.4.0 or newer ([LM Studio authentication](https://lmstudio.ai/docs/developer/core/authentication), [Anthropic messages](https://lmstudio.ai/docs/developer/anthropic-compat/messages)).
- **vLLM** listens on `http://localhost:8000`, exposes `/v1/models`, `/v1/chat/completions`, `/v1/completions`, and takes `--api-key` or `VLLM_API_KEY`, accepting any of several keys ([vLLM quickstart](https://docs.vllm.ai/en/stable/getting_started/quickstart/)).
- **llama-server** defaults to `127.0.0.1:8080`, takes `--api-key`, `--api-key-file`, or `LLAMA_API_KEY`, and keeps `/health` public and unauthenticated ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).

**Two design consequences.** First, ADR 0070's verdict triad (works / rejected / could-not-check) does not fit a runtime with no credential: a 200 proves the server is up, nothing more. Give the local kind its own probe act whose verdict names reachability, and use `GET /api/version` for Ollama (returns `{"version": "0.12.6"}`, MIT-licensed spec) ([Ollama get version](https://docs.ollama.com/api-reference/get-version)) rather than a model list, so an empty model library does not read as a failure. Second, the token is optional on three of the four runtimes, which strains ADR 0069's rule that "the account row splits by kind, and only the credentialed kinds carry a `credentialRef` field at all". An `aggregator` kind (key required) and a `localRuntime` kind (token optional) keep that split a parse error rather than a review note; folding locals into the credentialed kind would make the required field optional and lose the gate.

### 4. Model enumeration: fetch live, never hard-code, and expect the documented failure modes

What each side exposes:

| Source     | Endpoint                                                 | Notable fields                                                                                                                                                                                                                                                        |
| ---------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenRouter | `GET /api/v1/models`                                     | `id`, `name`, `context_length`, `pricing` (prompt/completion/image/cache read/write), `supported_parameters`, `architecture.modality`, `top_provider` ([ref](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties))               |
| Groq       | `GET /openai/v1/models`                                  | `id`, `active`, `context_window`, `max_completion_tokens` ([ref](https://console.groq.com/docs/models))                                                                                                                                                               |
| Ollama     | `GET /api/tags`, `GET /api/ps`                           | installed: `name`, `size`, `details.parameter_size`, `quantization_level`; loaded: `expires_at`, `size_vram` ([ref](https://ollama.readthedocs.io/en/api/))                                                                                                           |
| LM Studio  | `GET /api/v0/models` (v0), `GET /api/v1/models` (0.4.0+) | `state` ("not-loaded"/"loaded"), `max_context_length`, `arch`, `quantization`, `compatibility_type`; v1 adds `models/load`, `models/unload`, `models/download` ([v0](https://lmstudio.ai/docs/developer/rest/endpoints), [v1](https://lmstudio.ai/docs/api/rest-api)) |

LibreChat is the best-documented prior art for the fetch-vs-static decision, and its caveats read like a defect list you can pre-empt: `models.fetch: true` pulls the live list while `default` seeds the selection; wildcard gateways return only a single `*` entry that cannot populate a list; Apple MLX does not support fetching at all; Anthropic-native custom endpoints do not use OpenAI-style fetch; and Ollama needs its endpoint `name` to start with "ollama" ([LibreChat custom endpoints](https://www.librechat.ai/docs/quick_start/custom_endpoints), [AI endpoints](https://www.librechat.ai/docs/configuration/librechat_yaml/ai_endpoints)). OpenCode records the converse pain from the static side: users hand-listing local models "is tedious and error-prone since local models change frequently as they are loaded/unloaded", which is why auto-discovery from `/v1/models` is a recurring request ([issue #6231](https://github.com/anomalyco/opencode/issues/6231)).

**Recommendation.** Fetch on demand into the renderer's picker, keep a manual model-name entry as the escape hatch, and never cache a model list as the truth for routing. For LM Studio, prefer `state == "loaded"` over the bare list so a virtual model does not point at something that needs a cold load.

### 5. Catalogue metadata: models.dev is the right reference, the wrong dependency

[models.dev](https://models.dev/) is MIT-licensed, stores data as per-provider TOML validated in CI against `packages/core/src/schema.ts`, and publishes `api.json` (provider data), `models.json` (provider-agnostic model facts), and `catalog.json` (both), plus `/logos/{provider}.svg` ([repo](https://github.com/sst/models.dev)). Provider entries carry the `api` base URL and an `npm` field naming the AI SDK package, and the catalogue covers provider IDs, model IDs, endpoints, env var names, context windows, costs, modality, and status. OpenCode, which consumes it, provides `OPENCODE_MODELS_URL` and `OPENCODE_MODELS_PATH` so the registry can be loaded from a local file with no network ([OpenCode models](https://opencode.ai/v2/docs/models)).

**Trade-off.** It solves the aggregator display problem (hundreds of model IDs with no context window or price on some vendors' `/models`), but `README.md` claims recompose is "offline-first and private: no signup, no telemetry", and a startup fetch to a third-party host contradicts that. It also does not cover local runtimes: local providers are conventionally hand-declared as `@ai-sdk/openai-compatible` entries with a `baseURL`, not catalogue rows ([issue #6231](https://github.com/anomalyco/opencode/issues/6231)). **Recommend**: vendor a pinned snapshot for display metadata only, keep the live provider list authoritative for what a gateway may route to, and never put the catalogue on the request path. One conflict to resolve before you cite it: the site footer links `github.com/sst/models.dev` while search results and the OpenCode issue tracker say `anomalyco/models.dev` (likely an org rename), so confirm the canonical slug in the ADR.

### 6. Library choice for the target adapters

- **Hand-rolled fetch in the engine** (status quo per ADR 0070, which puts the probe in `packages/engine/src/provider/` behind a `probe` directive and notes the engine "already knows both vendors' path families in `gateway-app.ts`"). Fits ADR 0057 (Hono) and the `desktop-not-into-engine` wall in `.dependency-cruiser.cjs`. For a proxy that forwards and streams SSE, an SDK client mostly costs you a parse-and-reserialize round trip.
- **`@ai-sdk/openai-compatible`** is the best documented catalogue of per-provider quirks even if you do not adopt it: `createOpenAICompatible({ name, apiKey, baseURL, headers })` where `apiKey` becomes a Bearer header applied before custom headers, plus `queryParams` (Azure's `api-version`), a custom `fetch` seam for tests, `transformRequestBody` "for proxy providers that may require a different request format", and `metadataExtractor` for non-standard response fields. LM Studio is listed as OpenAI-compatible; Ollama and OpenRouter sit under community providers ([AI SDK docs](https://ai-sdk.dev/providers/openai-compatible-providers)).
- **LiteLLM** is Python and therefore out of scope as a dependency, but its config is the reference shape for the escape hatch: `model: openai/<name>` plus `api_base`, with the explicit warning not to append paths such as `/v1/embedding` to the base URL because the client adds them ([LiteLLM OpenAI-compatible](https://docs.litellm.ai/docs/providers/openai_compatible)).

**Recommendation**: keep the engine's hand-rolled fetch and borrow the quirk list rather than the dependency. This is a judgement call on my part, not a documented finding; the strongest counter-argument is that `queryParams` and header-ordering behaviour are exactly the details a hand-rolled adapter gets wrong on the second vendor.

### 7. An aggregator is itself a router, and that overlaps recompose's routers

OpenRouter's provider routing takes `provider.order` (slugs tried in sequence), `provider.allow_fallbacks` (**default `true`**), `provider.sort`, `provider.only`, `provider.ignore`, `provider.data_collection`, and `provider.require_parameters`; by default it load-balances across providers and retries backups on error, and only `allow_fallbacks: false` makes the request fail once your list is exhausted ([provider routing](https://openrouter.ai/docs/features/provider-routing)). It also ships an Auto Router (`model: "openrouter/auto-beta"`) that classifies the prompt and builds its own fallback chain ([model routing](https://openrouter.ai/docs/features/model-routing)).

**Implication.** `README.md` sells "failover ladders send traffic to the topmost healthy target". Stacked on OpenRouter, a healthy verdict means OpenRouter is healthy, not that the named model's upstream is: recompose's ladder can never see the failure it was built to react to, because the aggregator already absorbed it (at a price the user did not choose). Two honest options: expose `allow_fallbacks: false` / `provider.only` on an aggregator target so recompose's ladder is the only ladder, or document that an aggregator target is a black-box pool and let the aggregator route. Either way it belongs in the ADR, because silently double-routing is the kind of thing that surfaces as a billing surprise.

One naming conflict to verify: OpenRouter's authentication page shows the optional attribution header as `X-OpenRouter-Title` alongside `HTTP-Referer` ([authentication](https://openrouter.ai/docs/api_reference/authentication)), while most community material uses `X-Title`. Confirm against `openapi.yaml` before hard-coding either.

### 8. Discovery UX: well-known ports plus live enumeration, never a scan

No mainstream client scans the network. Continue exposes an explicit `AUTODETECT` model that enumerates whatever the local Ollama has ([Continue Ollama guide](https://docs.continue.dev/guides/ollama-guide)); Cline has you pick Ollama and type `http://localhost:11434`, then picks the model from the detected list, with no key ([Cline local models](https://docs.cline.bot/running-models-locally/overview)); Cherry Studio ships a provider entry where the key field is simply left blank ([Cherry Studio Ollama](https://docs.cherry-ai.com/docs/en-us/pre-basic/providers/ollama)). OpenCode carries per-runtime modules (`provider/local/ollama.ts`, `lmstudio.ts`, `llamacpp.ts`) and is working toward probing loaded models ([issue #6231](https://github.com/anomalyco/opencode/issues/6231)).

**Recommendation.** One button that probes the two known defaults (`127.0.0.1:11434`, `127.0.0.1:1234`) and reports found-or-not, with the base URL always editable and an optional token field. No port sweep: it is a firewall-prompt generator on macOS, it adds a scanning behaviour to an app whose pitch is "no telemetry", and the two ports cover the two runtimes `README.md` names.

---

### Recommendation summary

1. Model the two families as two kinds in the account schema, `aggregator` (key required, `credentialRef` present) and `localRuntime` (base URL required, token optional), so ADR 0069's kind split stays a parse-error gate.
2. Move the probe's base URL into the provider descriptor and stop assuming `/v1`; use `GET /api/v1/key` for OpenRouter, `GET {base}/models` for Bearer-key vendors, and `GET /api/version` for Ollama.
3. Give the local kind a reachability verdict distinct from the credential verdict, and keep ADR 0070's rule that no verdict is stored.
4. Enumerate models live per target with a manual override; prefer LM Studio's `state == "loaded"`; expect the LibreChat failure modes.
5. Treat dialect (OpenAI skin, Anthropic skin, both) as a target property so Anthropic-native targets pass through untranslated.
6. Decide the aggregator-routing overlap explicitly in the ADR; do not let two failover ladders stack silently.
7. Use models.dev as a pinned offline snapshot for display metadata only, never on the request path.
