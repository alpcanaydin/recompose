# 0040: The edit-time test-first gate

**Status**: Accepted
**Date**: 2026-07-27

## Context

This Architecture Decision Record (ADR) follows ADR-0038 and ADR-0039. ADR-0038 defined the feature cycle and deferred the edit-time test-first gate on its rollout list, naming `tdd-guard` as the tool. This record closes that item and replaces the tool.

The cycle states test-first discipline in prose and checks it after the fact. A reviewer holding a finished branch can't tell a captured red run from one written after the code. The tool boundary is the one place that sees an edit before it lands, and Claude Code exposes it through `PreToolUse` hooks. Getting a gate there took two tool evaluations and one live measurement that reversed the design, and this record is their permanent home. The behavioral contract lives in the `development-process` capability under `openspec/specs/`.

Two defects in the surrounding tooling landed with the change. The formatter hook failed a script edit under `.claude` when the file's extension sat in its pattern list, which skips `.mts` and matched one file at the time. It gained the flag that turns an out-of-scope path into a no-op. The review marker bound each fix push to a whole-branch review, and the incremental convention below cuts that cost.

One number stays out on purpose. The compliance figure in the frozen feature-cycle design note has no locatable primary source, so this record argues from the mechanism instead.

## Decision

recompose blocks an implementation edit that no failing test precedes, at the tool boundary, in the orchestrating session and in every subagent alike. The gate completes a three-tier stack. Edit-time enforcement fires before the code exists, the task report carries the captured red run for the reviewer, and the pull request runs the deterministic gates. Each tier catches what the others miss, and none replaces another.

- **Probity replaced the tool the rollout note named.** The change opened against `tdd-guard`, and reading its source turned the choice over. It keeps test state in fixed filenames under one project-root data directory, with plain unlocked writes and no session or subagent component in the path. This pipeline runs parallel implementers in separate worktrees, so one cluster's test state would answer for another's, and no configuration fixes that. Its README also steers new projects to Probity, its successor. Probity reads the host's session transcript and carries no state of its own, which removes the shared-state failure outright.
- **The gate pins exact as a root development dependency, never through the upstream plugin.** The lockfile records the version, and Renovate puts every update through review. The plugin runs the package unpinned on every matching tool call, so a tool that ships weekly would change behavior inside a hot path with no review. The pin has a footprint the design never priced. The lockfile gains 98 packages, counted as added `resolution:` entries, or 112 unique `name@version` keys once the `snapshots:` mirror counts peer-resolved variants, across 930 added lines and none removed. Three vendor software development kits arrive as hard dependencies, and this repository invokes one. They stay development-only, and upstream offers no lighter install.
- **The scope is an allow list over the source trees.** `probity.config.ts` binds the test-first rule to `apps/*/src/**` and `packages/*/src/**` and negates tests, type-level specs, stories, generated modules, stylesheets, and markup. Writing a test never trips the rule that demands one. The tree-wide globs replaced two named trees during arming, so a new package or a new extension arrives guarded. Only the stylesheet and markup negations name extensions. The other five negate the file's shape, such as `*.test.*`, so a test keeps its exemption under any extension, including a `.test.mts`. An allow list also beat the predecessor's deny list on a live trap. A deny pattern for `.claude` covered every worktree under `.claude/worktrees`, so the gate went inert in the worktrees it targets. Globs resolve against the configuration file's own directory, and every worktree carries its own committed copy, so no absolute path appears anywhere.
- **A resolver hands the gate the acting subagent's own record.** One live measurement reversed the design mid-change. A subagent's `PreToolUse` payload carries the parent session's transcript path, byte-identical to the main loop's, and the payload also carries `agent_id`. The per-subagent record sits at the transcript path with `.jsonl` stripped, then `subagents/agent-<agent id>.jsonl`. Without the resolver the gate reads a record holding none of the acting subagent's work, so it denies every implementer edit. The resolver at `.claude/workflows/hooks/resolve-transcript.mts` rewrites the path when the derived record exists and passes the payload through when it doesn't. Its ceiling is plain: the derived path is a convention the harness never documented. The fallback and the arming probe are the containment when that convention moves.
- **The gate is a probabilistic tier, never the gate of record.** A model judges each in-scope edit, and the project rules keep prohibitions in deterministic gates. Patch coverage, the diff-scoped mutation run, and the adversarial review stay the merge blockers. The tier has a matching character, and the arming probe observed it: a whitespace-only in-scope edit with no failing test passed, because the gate judges semantic behavior change rather than byte diffs. The formatter hook reverts that churn anyway, so the pass is a characteristic of the tier, not a defect.
- **The matcher covers the editing tools and leaves the shell path open.** Upstream's matcher also covers shell commands, which would close the path where a worker writes through the shell. This repository runs a constant stream of shell commands, and a transcript parse in front of each one taxes work the rule never targets. The trust model stays drift protection, and widening the matcher to the shell path is the named upgrade if drift shows up.
- **A denial costs seconds, and the cost scales with the transcript.** Against a 3.4-megabyte session transcript, a model-backed denial took 7.88 seconds of wall clock. A payload-validation denial short-circuits at 0.13 seconds with no model call. The implementation reference's "under 8 seconds" sources from this measurement, and the transcript size travels with the number because a longer session costs more.
- **Hook commands name their scripts through the project directory, never the working directory.** A hook handler runs in the session's current directory, and Claude Code changes that directory as the session moves. Both hooks named their targets relative to that directory, and both broke away from the checkout root. They broke in opposite ways. The gate's launcher died at `MODULE_NOT_FOUND` and exited 1. Only exit code 2 blocks a `PreToolUse` call, so exit 1 let the edit through and the gate went quiet. A quiet gate and a permitting gate look identical, so this is the worst failure the design has. The formatter's linter call failed, the hook turned that into exit 2, and every edit met a block. Both commands now anchor on the `${CLAUDE_PROJECT_DIR}` placeholder, which the harness expands to the project root. The resolver derives the gate binary from `import.meta.url` and runs the gate inside that checkout, so the gate still reads the checkout's own `probity.config.ts`. Anchoring the binary alone would trade silence for noise, because a gate that can't find its configuration denies every edit.
- **The design fails closed, and the timeout is one inferred fail-open edge.** A missing gate binary blocks every edit, in scope or not, because scope filtering lives inside the gate and a gate that never starts filters nothing. Only an incomplete install reaches that state now, since the resolver derives the binary from its own location. The timeout reading is an inference, not documented behavior. The hooks documentation states a non-blocking timeout only for HTTP hooks, and it marks that as a difference from command hooks. The harness's software development kit treats a callback hook timeout as blocking. The best-supported reading of the exit-code contract says a command hook killed for exceeding its timeout doesn't block. That reading makes the 120-second timeout the one fail-open edge in an otherwise fail-closed design, and the measured 7.88 seconds sits about fifteen times under it. An upstream statement of the command-hook timeout contract would settle the inference, as would a probe that forces the hook past its timeout.
- **The arming probe is the gate's acceptance evidence, in both directions.** The maintainer restarted a session inside the worktree and ran five checks. Configuration discovery resolved the worktree's own `probity.config.ts` rather than the parent checkout's. A parent resolution would bind the rule to the parent's trees and report nothing. The gate denied an in-scope behavioral edit with no failing test, and its file-specific verdict stated the session showed no failing test for the new behavior. After a failing test ran red in the same session, the identical edit proceeded. Test-file, markdown, and `.claude` edits passed untouched. A whitespace-only edit to an in-scope source file with no failing test also passed, which is the tier characteristic above. The denial's wording carries the proof that the gate read the acting subagent's own record, because it described that session's contents.
- **Deterministic specs cover the plumbing, and the verdict stays a probe.** Specs cover the transcript derivation's three branches, the formatter hook's scope invariant, and the pipe between the resolver and the gate. One case pins that a decision on standard output reaches the caller unchanged. That regression carries weight because the gate answers allow and deny alike with exit status 0, so a resolver that captures standard output turns the gate off while every check stays green. Further cases drive both hook commands and the resolver from a working directory outside the checkout, which pins the anchoring above. The gate's own verdict has no automated spec, by decision, because such a spec would spend a model call and return a soft answer. The recorded arming probe stays its check, and a reviewer reruns it after a gate update.
- **The heavy review reruns against the increment.** The first `review-pr` pass takes the pull request base, and each later pass takes the previous reviewed head as `baseSha`. One ceiling comes with the convention. The path guard reads only whether the head carries the status, so it can't walk the chain of reviewed ranges, and nothing confirms the chain covers the branch. ADR-0039 already scopes the marker to drift protection, and this ceiling sits inside that scope. The named upgrade writes the reviewed range into the status description, so the guard can walk one link of the chain.

## Alternatives

- **Staying on `tdd-guard`**: rejected. The storage model fails under parallel worktrees, and its own README steers new projects to the successor.
- **The upstream plugin, alone or alongside the pin**: rejected. Its hook runs the package unpinned in a hot path, and a plugin update can restore that hook with no signal.
- **Guarding everything and excluding by exception**: rejected. The exception list is the failure mode the predecessor demonstrated, and the worktree trap proved it live.
- **The upstream matcher verbatim, shell commands included**: deferred. The latency tax across a shell-heavy repository outweighs the drift risk today, and the widening stays the named upgrade.
- **Waiting for upstream to resolve the subagent record itself**: rejected. The upstream tracker never mentions subagents, and the pipeline needs the gate now. One top-level session per worktree, or serial clusters, would each trade a working dispatch model for twelve lines of derivation.
- **An automated spec over the gate's verdict**: rejected. It would spend a model call per run and return a soft answer, so the recorded probe is the honest check.
- **Chain verification for the review marker now**: deferred. The convention alone cuts the re-review cost, and ADR-0039's trust model already owns the boundary.

## Consequences

**Good**: an implementation edit with no failing test in the acting session meets a blocked tool call, in the orchestrating session and in every subagent alike. The gate carries no shared state, so parallel worktree clusters never answer for each other. The scope keeps documents, specifications, configuration, and tooling editable, and writing a test never blocks. A fix push pays for an incremental review pass instead of a whole-branch one. Rollback is one hook entry.

**Bad, and accepted**: each in-scope edit that misses the fast path spends a model call, and the allow list is the only cost control. The verdict is probabilistic, so the deterministic gates stay the proof of discipline. The resolver rests on a path convention the harness never documented, with the fallback and the probe as the containment. A broken gate fails closed and stops every edit until the maintainer intervenes. Shell-driven writes skip the gate. The pin carries three vendor software development kits for the one the gate invokes.
