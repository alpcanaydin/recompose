# 0040: The edit-time test-first gate

**Status**: Accepted
**Date**: 2026-07-27

## Context

This Architecture Decision Record (ADR) follows ADR-0038 and ADR-0039. ADR-0038 defined the feature cycle and deferred the edit-time test-first gate on its rollout list, naming `tdd-guard` as the tool. This record closes that item and replaces the tool.

The cycle states test-first discipline in prose and checks it after the fact. A reviewer holding a finished branch can't tell a captured red run from one written after the code. The tool boundary is the one place that sees an edit before it lands, and Claude Code exposes it through `PreToolUse` hooks. Getting a gate there took two tool evaluations and one live measurement that reversed the design, and this record is their permanent home. The behavioral contract lives in the `development-process` capability under `openspec/specs/`.

Two defects in the surrounding tooling landed with the change. The formatter hook failed a script edit under `.claude` when the file's extension sat in its pattern list, which skips `.mts` and matched one file at the time. It gained the flag that turns an out-of-scope path into a no-op. The review marker bound each fix push to a whole-branch review, and the incremental convention below cuts that cost.

One number stays out on purpose. The compliance figure in the frozen feature-cycle design note has no locatable primary source, so this record argues from the mechanism instead.

## Decision

recompose blocks an implementation edit that no failing test precedes, at the tool boundary, in the orchestrating session and in every subagent alike. The gate completes a three-tier stack. Edit-time enforcement fires before the code exists, the task report carries the captured red run for the reviewer, and the pull request runs the deterministic gates. Each tier catches what the others miss, and none replaces another.

- **Probity replaced the tool the rollout note named.** The change opened against `tdd-guard`, and reading its source turned the choice over. It keeps test state in fixed filenames under one project-root data directory, with plain unlocked writes and no session or subagent component in the path. This pipeline runs parallel implementers in separate worktrees, so one cluster's test state would answer for another's, and no configuration fixes that. Its README also steers new projects to Probity, its successor. Probity reads the host's session transcript and carries no state of its own, which removes the shared-state failure outright.
- **The gate pins exact as a root development dependency, never through the upstream plugin.** The lockfile records the version, and Renovate puts every update through review. The plugin runs the package unpinned on every matching tool call, so a tool that ships weekly would change behavior inside a hot path with no review. The pin has a footprint the design never priced. The lockfile gains 98 packages, counted as added `resolution:` entries, or 112 unique `name@version` keys once the `snapshots:` mirror counts peer-resolved variants, across 930 added lines and none removed. Three vendor software development kits arrive as hard dependencies, and this repository invokes one. They stay development-only, and upstream offers no lighter install.
- **The scope is an allow list over the source trees.** `probity.config.ts` binds the test-first rule to `apps/*/src/**` and `packages/*/src/**` and negates tests, type-level specs, stories, generated modules, stylesheets, and markup. Writing a test never trips the rule that demands one. The tree-wide globs replaced two named trees during arming, so a new package or a new extension arrives guarded. Only the stylesheet and markup negations name extensions. The other five negate the file's shape, such as `*.test.*`, so a test keeps its exemption under any extension, including a `.test.mts`. An allow list also beat the predecessor's deny list on one trap. A deny pattern for `.claude` covered every worktree under `.claude/worktrees`, so the gate went inert in the worktrees it targets. Globs resolve against the configuration file's own directory, and every worktree carries its own committed copy, so no absolute path appears anywhere. The allow list alone didn't clear the worktree trap, though. The review found a second form of it in the resolver, and the defect entry below carries the correction.
- **A resolver hands the gate the acting subagent's own record.** One live measurement reversed the design mid-change. A subagent's `PreToolUse` payload carries the parent session's transcript path, byte-identical to the main loop's, and the payload also carries `agent_id`. The harness keeps that record under the transcript path with `.jsonl` stripped, then `subagents/`, and the defect entry below covers the two layouts it uses there. Without the resolver the gate reads a record holding none of the acting subagent's work, so it denies every implementer edit. The resolver at `.claude/workflows/hooks/resolve-transcript.mts` rewrites the path when it finds the record and passes the payload through when it doesn't. Its ceiling is plain: the derived path is a convention the harness never documented. The fallback and the arming probe are the containment when that convention moves.
- **The gate is a probabilistic tier, never the gate of record.** A model judges each in-scope edit, and the project rules keep prohibitions in deterministic gates. Patch coverage, the diff-scoped mutation run, and the adversarial review stay the merge blockers. The tier has a matching character, and the arming probe observed it: a whitespace-only in-scope edit with no failing test passed, because the gate judges semantic behavior change rather than byte diffs. The formatter hook reverts that churn anyway, so the pass is a characteristic of the tier, not a defect.
- **The matcher covers the editing tools and leaves the shell path open.** Upstream's matcher also covers shell commands, which would close the path where a worker writes through the shell. This repository runs a constant stream of shell commands, and a transcript parse in front of each one taxes work the rule never targets. The trust model stays drift protection, and widening the matcher to the shell path is the named upgrade if drift shows up.
- **A denial costs seconds, and the cost scales with the transcript.** Against a 3.4-megabyte session transcript, a model-backed denial took 7.88 seconds of wall clock. A payload-validation denial short-circuits at 0.13 seconds with no model call. The implementation reference's "under 8 seconds" sources from this measurement, and the transcript size travels with the number because a longer session costs more.
- **Hook commands name their scripts through the project directory, never the working directory.** A hook handler runs in the session's current directory, and Claude Code changes that directory as the session moves. Both hooks named their targets relative to that directory, and both broke away from the checkout root. They broke in opposite ways. The gate's launcher died at `MODULE_NOT_FOUND` and exited 1. Only exit code 2 blocks a `PreToolUse` call, so exit 1 let the edit through and the gate went quiet. A quiet gate and a permitting gate look identical, so this is the worst failure the design has. The formatter's linter call failed, the hook turned that into exit 2, and every edit met a block. Both commands now anchor on the `${CLAUDE_PROJECT_DIR}` placeholder, which the harness expands to the project root. The resolver derives the gate binary from `import.meta.url`, so an uninstalled worktree still reaches a working gate. Anchoring the binary alone would trade silence for noise, because a gate that can't find its configuration denies every edit. The scope anchor is a separate question from the binary anchor, and the defect entry below settles it.
- **The design fails closed on the paths it covers, and the review below found the ones it missed.** A missing gate binary blocks every edit, in scope or not, because scope filtering lives inside the gate and a gate that never starts filters nothing. Only an incomplete install reaches that state now, since the resolver derives the binary from its own location. The heavy adversarial review then reproduced four fail-open paths that this list once called closed, and the "Defects the review found" section below carries each one with its fix. The timeout is one more inferred edge, and the timeout reading is an inference rather than documented behavior. The hooks documentation states a non-blocking timeout only for HTTP hooks, and it marks that as a difference from command hooks. The harness's software development kit treats a callback hook timeout as blocking. The best-supported reading of the exit-code contract says a command hook killed for exceeding its timeout doesn't block. That reading makes the 120-second timeout the one fail-open edge in an otherwise fail-closed design, and the measured 7.88 seconds sits about fifteen times under it. An upstream statement of the command-hook timeout contract would settle the inference, as would a probe that forces the hook past its timeout.
- **The arming probe is the gate's acceptance evidence, in both directions.** The maintainer restarted a session inside the worktree and ran five checks. Configuration discovery resolved the worktree's own `probity.config.ts` rather than the parent checkout's. A parent resolution would bind the rule to the parent's trees and report nothing. The gate denied an in-scope behavioral edit with no failing test, and its file-specific verdict stated the session showed no failing test for the new behavior. After a failing test ran red in the same session, the identical edit proceeded. Test-file, markdown, and `.claude` edits passed untouched. A whitespace-only edit to an in-scope source file with no failing test also passed, which is the tier characteristic above. The denial's wording carries the proof that the gate read the acting subagent's own record, because it described that session's contents.
- **Deterministic specs cover the plumbing, and the verdict stays a probe.** Specs cover the transcript derivation's three branches, the formatter hook's scope invariant, and the pipe between the resolver and the gate. One case pins that a decision on standard output reaches the caller unchanged. That regression carries weight because the gate answers allow and deny alike with exit status 0, so a resolver that captures standard output turns the gate off while every check stays green. Further cases drive both hook commands and the resolver from a working directory outside the checkout, which pins the anchoring above. The review added four more: a launch through a symlinked parent, the gate configuration a worktree edit selects, a launcher that meets a Node too old to load the resolver, and a subagent record a saved workflow keeps. The gate's own verdict has no automated spec, by decision, because such a spec would spend a model call and return a soft answer. The recorded arming probe stays its check, and a reviewer reruns it after a gate update.
- **The heavy review reruns against the increment.** The first `review-pr` pass takes the pull request base, and each later pass takes the previous reviewed head as `baseSha`. One ceiling comes with the convention. The path guard reads only whether the head carries the status, so it can't walk the chain of reviewed ranges, and nothing confirms the chain covers the branch. ADR-0039 already scopes the marker to drift protection, and this ceiling sits inside that scope. The named upgrade writes the reviewed range into the status description, so the guard can walk one link of the chain.

## Defects the review found

A heavy adversarial review ran over the armed gate and reproduced four defects. Two of them turned the gate off in silence, which the record above names the worst failure this design has.

- **The entry guard compared unresolved paths, so one symlink turned the gate off.** The guard compared `process.argv[1]` against `fileURLToPath(import.meta.url)`. Node leaves symlinks intact in `process.argv[1]` and resolves them in `import.meta.url`. One aliased directory anywhere in the launch path broke the match, so `main` never ran and the hook exited 0 with empty output. A `PreToolUse` hook that exits 0 with no output states no opinion, so the edit landed. macOS aliases `/tmp` onto `/private/tmp`, and a checkout under any aliased parent hit this. `import.meta.main` now decides the entry, and Node derives that flag from the module graph rather than from a path string. The specification couldn't catch the defect, because it built its scratch checkout through `realpathSync` and erased the trigger. A new case reaches the resolver through a deliberate symlink, which holds on every platform rather than only where the system aliases its temporary directory. The path guard at `.claude/workflows/path-guard/path-guard.mts` carried the same idiom and took the same fix, since a guard that never runs reports success to the workflow that called it.

- **The gate judged every edit against one checkout, so it skipped the worktrees it exists to guard.** The resolver pinned the child's working directory to its own checkout, the gate walked up from there for `probity.config.ts`, and the load step rewrote `apps/*/src/**` into that root's absolute form. Any path outside that one root matched no rule, so the gate returned empty output and exit 0, which permits. The implementation phase runs one implementer per cluster in its own worktree, and those subagents inherit the orchestrating session's project directory, so the gate stayed inert for exactly the edits it targets. A run against the real binary reproduced it. A write inside the session checkout drew a deny, and the byte-identical write into a sibling worktree returned exit 0 with both streams empty. A worktree nested at `.claude/worktrees/cluster-1` skipped too, because a single `*` never crosses a slash. The resolver now reads the action's file path from the payload, walks up from that file for the nearest `probity.config.ts`, and passes it to the gate through `--config`. The gate then judges an edit against the checkout that owns the file rather than the checkout that owns the resolver. An edit that no configuration covers falls back to the resolver's own checkout, which keeps a scratch file outside every checkout out of scope instead of blocking it. The binary still comes from the resolver's checkout, so a worktree needs no install and a worktree that predates this change needs no new file.

- **The hook launched a TypeScript file on an undeclared Node, so an old Node disarmed the session.** The hook ran a `.mts` file through bare `node` from the operator's path, and nothing in the repository stated a Node floor. `mise.toml` pinned only vale and gitleaks, `package.json` carried no `engines` block, and no `.nvmrc` or `.node-version` existed. Node strips types without a flag from 22.18 and from 23.6, and older releases die at `ERR_UNKNOWN_FILE_EXTENSION` with exit 1 and empty standard output. Exit 1 is a non-blocking error, so the gate went quiet for the whole session. Continuous integration pins Node 24, so no gate caught it, and the exposure sat entirely on the developer machine where this gate does its work. The load failure happens before any project code runs, so a check inside the `.mts` file can't help. A plain `.mjs` launcher at `.claude/workflows/hooks/launch-gate.mjs` now holds the hook entry, runs on any Node, and starts the resolver as a child. A child that exits 1 never produced a decision, so the launcher rewrites that into exit 2 and names both the running Node and the required range. `package.json` declares `engines.node` as `^22.18.0 || >=23.6.0`, and a specification ties the launcher's message to that declaration. The rewrite also covers a resolver that crashes for any other reason, which suits a design that fails closed. One ceiling stays: an operator with no `node` on the path at all never reaches the launcher, and closing that needs a shell wrapper this repository doesn't want.

- **The record derivation computed one path, and a saved workflow keeps its subagents somewhere else.** The resolver built `<transcript minus .jsonl>/subagents/agent-<agent id>.jsonl`. That path holds for a subagent the Task tool dispatched at any depth. A subagent a saved workflow dispatched keeps its record one level deeper, under `subagents/workflows/wf_<workflow id>/agent-<agent id>.jsonl`. The derivation missed, the resolver fell back to the parent session transcript, and the gate judged that subagent against a record holding none of its work. That's the exact cross-session reading the resolver exists to prevent. A check against this machine's session directory confirmed both layouts. The payload carries the subagent identity and never the workflow identity, so the resolver now lists the `workflows` directory and searches each workflow for a record named after the acting subagent. The Task tool layout stays the first candidate, the fallback to the session transcript stays, and the announcement on standard error still names the record it sought.

## The defect the first anchoring fix introduced

The anchoring fix above pinned the formatter hook to the session's project directory. It cured one anchoring bug and planted a second one. A record that hides its own mistakes teaches nothing, so this section names it.

- **The formatter judged every edit from the session's checkout, so a sibling worktree met a block on every edit.** The hook opened with `cd "${CLAUDE_PROJECT_DIR}"`, which stops a drifting working directory from breaking it. The project directory belongs to the session, yet the edited file can sit in a different checkout. This repository runs one implementer per cluster in its own worktree, so that split is the normal case rather than an edge case. The linter walked up from the edited file and found the other checkout's `.oxlintrc.json`. It then rejected that file as a nested config, because `options.typeAware` holds only in a root config. The hook turned the failure into exit 2, so an implementer editing in its own worktree could land nothing. The correction reuses the rule the gate already carries. A shared module named the nearest ancestor of the edited file carrying a given marker, and both hooks called it. The section below renames that module and bounds its walk. The gate asks for `probity.config.ts`, and the formatter asks for `.oxlintrc.json`. The formatter then runs that checkout's `oxfmt` and `oxlint`, names both configurations through `--config`, and points the child processes at that checkout. An edit that no checkout covers falls back to the checkout owning the hook, which matches the gate's fallback and keeps a scratch file linted rather than blocked.

- **The hook left the settings file, because an inline snippet carries no specification.** Four defects in this class already moved logic into tested scripts, and this one makes five. `.claude/workflows/hooks/format-edit.mts` now holds the formatter, and the `node:test` suite covers it. Six cases pin the new behavior. A clean file in another checkout stands, that checkout's ignore list applies, and its formatter configuration applies too. A real lint error there still exits 2 and names the rule it broke, which keeps the blocking case from turning into silence. An edit no checkout covers still blocks. The original defect stays covered twice over, since the script reads no working directory and names both the toolchain and the configurations by absolute path. Breaking either anchor alone leaves the suite green, and breaking both turns the working-directory cases red.

## The defect the second anchoring fix introduced

The anchoring fix above let the edited file's path pick the checkout. It cured the sibling-worktree block and opened a path from a file write to a running program. The pattern repeats, so this section names it too.

- **The edited path chose the program, so a planted directory ran its own linter.** The shared module walked up from the edited file for `.oxlintrc.json`, and the directory it landed on became the checkout. The formatter hook then started `node_modules/.bin/oxlint` and `node_modules/.bin/oxfmt` from that directory. An actor who writes files plants `/somewhere/.oxlintrc.json` beside `/somewhere/node_modules/.bin/oxlint`, edits `/somewhere/x.ts`, and the hook starts the planted program. That matters more here than the raw capability suggests. The Bash tool passes through a permission classifier in this repository, and a file write doesn't, so the steering walks around a control the repository leans on. A specification now plants both files and checks that neither the planted linter nor the planted formatter ever starts.

- **A configuration steers execution too, so pinning the program alone leaves the hole open.** `.oxlintrc.json` carries a `jsPlugins` list, and oxlint loads every specifier it names. `probity.config.ts` is a TypeScript module that the gate imports. Either file turns a configuration choice into arbitrary code. The walk that picks a configuration therefore needs the same confinement as the walk that picked a program, and both walks now stop inside this repository.

- **The walk had no ceiling, so a stray configuration redirected the toolchain.** The ancestor list climbed to the filesystem root. One stray `.oxlintrc.json` in a home directory or a temporary directory then captured every edit below it. That fault needs no attacker, and it would have surfaced as a confusing toolchain mismatch rather than as a breach.

- **Git states the bound, and the check is exact rather than heuristic.** `.claude/workflows/hooks/repository-scope.mts` asks git for the edited file's repository root and its common git directory. A candidate qualifies only when its common directory matches the one the hook's own checkout reports. A sibling worktree qualifies, and an unrelated repository doesn't, even though both answer to git. The walk then climbs the number of levels git reports and halts at that worktree root. The check never compares directory names, so no symlink widens the bound. A path whose directories don't exist yet resolves through its nearest existing ancestor, which matters because `PreToolUse` fires before the write.

- **The program comes from the hook's own checkout, always.** `.claude/workflows/hooks/format-edit.mts` starts `oxlint` and `oxfmt` from the checkout holding the script and names the chosen configuration through `--config`. The gate resolver already worked this way, so it needed only the bound. Pinning the program also drops a cost the earlier entry accepted: the hook now formats and lints a worktree that carries no install. That holds only while the worktree's configuration names no JavaScript plugin, because oxlint resolves a plugin next to the configuration file rather than next to the program.

- **The suite grew from 50 cases to 65, and every property has a case that fails without it.** Breaking the program pin turns the uninstalled-worktree cases red. Dropping the repository match turns the planted-repository cases red. Removing the climb ceiling turns five cases red across both hooks and the bound's own unit specifications. Pinning the configuration to one checkout turns seven capability cases red. The fixtures moved with the fix. A sibling checkout is now a real worktree of this repository, and a planted checkout is a repository of its own, because a plain temporary directory exercised neither bound and let a first draft look finished.

## Alternatives

- **Staying on `tdd-guard`**: rejected. The storage model fails under parallel worktrees, and its own README steers new projects to the successor.
- **The upstream plugin, alone or alongside the pin**: rejected. Its hook runs the package unpinned in a hot path, and a plugin update can restore that hook with no signal.
- **Guarding everything and excluding by exception**: rejected. The exception list is the failure mode the predecessor demonstrated, and the worktree trap proved it live.
- **Confining the resolved checkout and still running its program**: rejected. It leaves the executable choice on the edited path, so the whole defense rests on the confinement being exactly right. Pinning the program keeps a foreign binary out of reach even when the bound has a bug, and it costs a worktree install rather than buying one.
- **The upstream matcher verbatim, shell commands included**: deferred. The latency tax across a shell-heavy repository outweighs the drift risk today, and the widening stays the named upgrade.
- **Waiting for upstream to resolve the subagent record itself**: rejected. The upstream tracker never mentions subagents, and the pipeline needs the gate now. One top-level session per worktree, or serial clusters, would each trade a working dispatch model for twelve lines of derivation.
- **An automated spec over the gate's verdict**: rejected. It would spend a model call per run and return a soft answer, so the recorded probe is the honest check.
- **Chain verification for the review marker now**: deferred. The convention alone cuts the re-review cost, and ADR-0039's trust model already owns the boundary.

## Consequences

**Good**: an implementation edit with no failing test in the acting session meets a blocked tool call, in the orchestrating session and in every subagent alike. The gate carries no shared state, so parallel worktree clusters never answer for each other. The scope keeps documents, specifications, configuration, and tooling editable, and writing a test never blocks. A fix push pays for an incremental review pass instead of a whole-branch one. Rollback is one hook entry.

**Bad, and accepted**: each in-scope edit that misses the fast path spends a model call, and the allow list is the only cost control. The verdict is probabilistic, so the deterministic gates stay the proof of discipline. The resolver rests on a path convention the harness never documented, with the fallback and the probe as the containment. A broken gate fails closed and stops every edit until the maintainer intervenes. Shell-driven writes skip the gate. The pin carries three vendor software development kits for the one the gate invokes.
