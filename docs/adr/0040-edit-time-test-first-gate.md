# 0040: The edit-time test-first gate

**Status**: Accepted
**Date**: 2026-07-27

## Context

This Architecture Decision Record (ADR) follows ADR-0038 and ADR-0039. ADR-0038 defined the feature cycle and deferred the edit-time test-first gate on its rollout list, naming `tdd-guard` as the tool. This record closes that item and replaces the tool.

The cycle states test-first discipline in prose and checks it after the fact. A reviewer holding a finished branch can't tell a captured red run from one written after the code. The tool boundary is the one place that sees an edit before it lands, and Claude Code exposes it through `PreToolUse` hooks. Getting a gate there took two tool evaluations and one live measurement that reversed the design, and this record is their permanent home. The behavioral contract lives in the `development-process` capability under `openspec/specs/`.

Two defects in the surrounding tooling landed with the change. The formatter hook failed a script edit under `.claude` when the file's extension sat in its pattern list, which skips `.mts` and matched one file at the time. It gained the flag that turns an out-of-scope path into a no-op. The review marker bound each fix push to a whole-branch review, and the incremental convention below cuts that cost.

One number stays out on purpose. The compliance figure in the frozen feature-cycle design note has no locatable primary source, so this record argues from the mechanism instead.

Only an incomplete install reaches that state now, since the resolver derives the binary from its own location. ## Defects the review found

A heavy adversarial review ran over the armed gate and reproduced four defects. Two of them turned the gate off in silence, which the record above names the worst failure this design has.

- **The entry guard compared unresolved paths, so one symlink turned the gate off.** The guard compared `process.argv[1]` against `fileURLToPath(import.meta.url)`. Node leaves symlinks intact in `process.argv[1]` and resolves them in `import.meta.url`. One aliased directory anywhere in the launch path broke the match, so `main` never ran and the hook exited 0 with empty output. A `PreToolUse` hook that exits 0 with no output states no opinion, so the edit landed. macOS aliases `/tmp` onto `/private/tmp`, and a checkout under any aliased parent hit this. A shared guard at `.claude/workflows/hooks/entry-point.mjs` now decides the entry. It resolves `process.argv[1]` through `realpathSync` before matching that path against the module's own URL, so an aliased parent no longer hides the entry. The first correction reached for `import.meta.main` instead, and the section below records what that cost. The specification couldn't catch the defect, because it built its scratch checkout through `realpathSync` and erased the trigger. A new case reaches the resolver through a deliberate symlink, which holds on every platform rather than only where the system aliases its temporary directory. The path guard at `.claude/workflows/path-guard/path-guard.mts` carried the same idiom and took the same fix, since a guard that never runs reports success to the workflow that called it.

- **The gate judged every edit against one checkout, so it skipped the worktrees it exists to guard.** The resolver pinned the child's working directory to its own checkout, the gate walked up from there for `probity.config.ts`, and the load step rewrote `apps/*/src/**` into that root's absolute form. Any path outside that one root matched no rule, so the gate returned empty output and exit 0, which permits. The implementation phase runs one implementer per cluster in its own worktree, and those subagents inherit the orchestrating session's project directory, so the gate stayed inert for exactly the edits it targets. A run against the real binary reproduced it. A write inside the session checkout drew a deny, and the byte-identical write into a sibling worktree returned exit 0 with both streams empty. A worktree nested at `.claude/worktrees/cluster-1` skipped too, because a single `*` never crosses a slash. The resolver now reads the action's file path from the payload, walks up from that file for the nearest `probity.config.ts`, and passes it to the gate through `--config`. The gate then judges an edit against the checkout that owns the file rather than the checkout that owns the resolver. An edit that no configuration covers falls back to the resolver's own checkout, which keeps a scratch file outside every checkout out of scope instead of blocking it. The binary still comes from the resolver's checkout, so a worktree needed no install and a worktree that predated the change needed no new file. That resolution went. Three later reviews broke the walk it rests on, and the section on the capability the boundary couldn't carry records the removal and the coverage the gate gave up with it.

- **The hook launched a TypeScript file on an undeclared Node, so an old Node disarmed the session.** The hook ran a `.mts` file through bare `node` from the operator's path, and nothing in the repository stated a Node floor. `mise.toml` pinned only vale and gitleaks, `package.json` carried no `engines` block, and no `.nvmrc` or `.node-version` existed. Node strips types without a flag from 22.18 and from 23.6, and older releases die at `ERR_UNKNOWN_FILE_EXTENSION` with exit 1 and empty standard output. Exit 1 is a non-blocking error, so the gate went quiet for the whole session. Continuous integration pins Node 24, so no gate caught it, and the exposure sat entirely on the developer machine where this gate does its work. The load failure happens before any project code runs, so a check inside the `.mts` file can't help. A plain `.mjs` launcher at `.claude/workflows/hooks/launch-gate.mjs` now holds the hook entry, runs on any Node, and starts the resolver as a child. A child that exits 1 never produced a decision, so the launcher rewrites that into exit 2 and names both the running Node and the required range. `package.json` declares `engines.node` as `^22.18.0 || >=23.6.0`, and a specification ties the launcher's message to that declaration. The rewrite also covers a resolver that crashes for any other reason, which suits a design that fails closed. One ceiling stays: an operator with no `node` on the path at all never reaches the launcher, and closing that needs a shell wrapper this repository doesn't want.

- **The record derivation computed one path, and a saved workflow keeps its subagents somewhere else.** The resolver built `<transcript minus .jsonl>/subagents/agent-<agent id>.jsonl`. That path holds for a subagent the Task tool dispatched at any depth. A subagent a saved workflow dispatched keeps its record one level deeper, under `subagents/workflows/wf_<workflow id>/agent-<agent id>.jsonl`. The derivation missed, the resolver fell back to the parent session transcript, and the gate judged that subagent against a record holding none of its work. That's the exact cross-session reading the resolver exists to prevent. A check against this machine's session directory confirmed both layouts. The payload carries the subagent identity and never the workflow identity, so the resolver now lists the `workflows` directory and searches each workflow for a record named after the acting subagent. The Task tool layout stays the first candidate, the fallback to the session transcript stays, and the announcement on standard error still names the record it sought.

## The defect the first anchoring fix introduced

The anchoring fix above pinned the formatter hook to the session's project directory. It cured one anchoring bug and planted a second one. A record that hides its own mistakes teaches nothing, so this section names it.

- **The formatter judged every edit from the session's checkout, so a sibling worktree met a block on every edit.** The hook opened with `cd "${CLAUDE_PROJECT_DIR}"`, which stops a drifting working directory from breaking it. The project directory belongs to the session, yet the edited file can sit in a different checkout. This repository runs one implementer per cluster in its own worktree, so that split is the normal case rather than an edge case. The linter walked up from the edited file and found the other checkout's `.oxlintrc.json`. It then rejected that file as a nested config, because `options.typeAware` holds only in a root config. The hook turned the failure into exit 2, so an implementer editing in its own worktree could land nothing. The correction reuses the rule the gate already carries. A shared module named the nearest ancestor of the edited file carrying a given marker, and both hooks called it. The section below renames that module and bounds its walk. The gate asks for `probity.config.ts`, and the formatter asks for `.oxlintrc.json`. The formatter then runs that checkout's `oxfmt` and `oxlint`, names both configurations through `--config`, and points the child processes at that checkout. An edit that no checkout covers falls back to the checkout owning the hook, which matches the gate's fallback and keeps a scratch file linted rather than blocked.

- **The hook left the settings file, because an inline snippet carries no specification.** Four defects in this class already moved logic into tested scripts, and this one makes five. `.claude/workflows/hooks/format-edit.mts` now holds the formatter, and the `node:test` suite covers it. Six cases pin the new behavior. A clean file in another checkout stands, that checkout's ignore list applies, and its formatter configuration applies too. A real lint error there still exits 2 and names the rule it broke, which keeps the blocking case from turning into silence. An edit no checkout covers still blocks. The original defect stays covered twice over, since the script reads no working directory and names both the toolchain and the configurations by absolute path. Breaking either anchor alone leaves the suite green, and breaking both turns the working-directory cases red.

## The defect the second anchoring fix introduced

The anchoring fix above let the edited file's path pick the checkout. It cured the sibling-worktree block and opened a path from a file write to a running program. The pattern repeats, so this section names it too.

- **The edited path chose the program, so a planted directory ran its own linter.** The shared module walked up from the edited file for `.oxlintrc.json`, and the directory it landed on became the checkout. The formatter hook then started `node_modules/.bin/oxlint` and `node_modules/.bin/oxfmt` from that directory. An actor who writes files plants `/somewhere/.oxlintrc.json` beside `/somewhere/node_modules/.bin/oxlint`, edits `/somewhere/x.ts`, and the hook starts the planted program. That matters more here than the raw capability suggests. The Bash tool passes through a permission classifier in this repository, and a file write doesn't, so the steering walks around a control the repository leans on. A specification now plants both files and checks that neither the planted linter nor the planted formatter ever starts.

- **A configuration steers execution too, so pinning the program alone leaves the hole open.** `.oxlintrc.json` carries a `jsPlugins` list, and oxlint loads every specifier it names. `probity.config.ts` is a TypeScript module that the gate imports. Either file turns a configuration choice into arbitrary code. The walk that picks a configuration therefore needs the same confinement as the walk that picked a program, and both walks now stop inside this repository.

- **The walk had no ceiling, so a stray configuration redirected the toolchain.** The ancestor list climbed to the filesystem root. One stray `.oxlintrc.json` in a home directory or a temporary directory then captured every edit below it. That fault needs no attacker, and it would have surfaced as a confusing toolchain mismatch rather than as a breach.

- **This entry asked git to state the bound, and three later reviews walked through it.** `.claude/workflows/hooks/repository-scope.mts` asked git for the edited file's repository root and its common git directory, and a candidate qualified only when its common directory matched the one the hook's own checkout reported. A sibling worktree qualified, an unrelated repository didn't, and the walk climbed the number of levels git reported and halted at that worktree root. This entry read the check as exact because it compared no directory names. That reading was wrong on both counts, and the section below carries what the reviews reproduced and what replaced the approach outright.

- **The program comes from the hook's own checkout, always.** `.claude/workflows/hooks/format-edit.mts` starts `oxlint` and `oxfmt` from the checkout holding the script and names the chosen configuration through `--config`. The gate resolver already worked this way, so it needed only the bound. Pinning the program also dropped a cost the earlier entry accepted: the hook formatted and linted a worktree that carried no install. That capability went too. It held only while the worktree's configuration named no JavaScript plugin, because oxlint resolves a plugin next to the configuration file rather than next to the program, and that exception turned out to be the whole hole.

- **The suite grew from 50 cases to 65, and every property had a case that failed without it.** Breaking the program pin turned the uninstalled-worktree cases red. Dropping the repository match turned the planted-repository cases red. Removing the climb ceiling turned five cases red across both hooks and the bound's own unit specifications. Pinning the configuration to one checkout turned seven capability cases red. The fixtures moved with the fix. A sibling checkout became a real worktree of this repository, and a planted checkout a repository of its own, because a plain temporary directory exercised neither bound and let a first draft look finished. Those counts describe a suite the section below shrank, and the fixtures outlived the mechanism that produced them.

## The defect the entry-guard fix introduced

The entry-guard fix above reached for `import.meta.main`. It closed the symlink hole on the newest Node builds and reopened the same silent permit on older ones. A later review caught it inside the range this repository declares supported, so this section names it.

- **The entry guard read a field the declared floor doesn't carry, so the gate went quiet across much of its supported range.** Node added `import.meta.main` in v24.2.0 and v22.18.0, and nothing between those releases carries it. This repository declares `^22.18.0 || >=23.6.0`. Every Node from 23.6.0 through 23.11.1, and from 24.0.0 through 24.1.x, strips types yet leaves the field undefined. `main` never ran, the hook exited 0 with empty standard output, and a `PreToolUse` hook that says nothing lets the edit land. The launcher only rewrites exit 1 into a block, so it forwarded that 0 unchanged. Real builds confirmed both ends. Node 26.5.0 answered a denying payload with exit 2, while Node 23.11.1 and Node 24.1.0 both exited 0 with empty output.

- **The same field sat in the blast-radius path guard, where a silent exit 0 reads as a pass.** `.claude/workflows/path-guard/path-guard.mts` runs in continuous integration. A guard that never runs still reports success, so a pull request touching a blast-radius path would merge without the heavy-review marker. With the required environment variables unset, Node 26.5.0 exited 1 and named the missing variable. Node 24.1.0 and Node 23.11.1 exited 0 with completely empty output.

- **The insight existed and landed in one place out of three.** The entry that introduced the field wrote in its own report that the launcher couldn't use `import.meta.main`. Older Node lacks it, and the gate would go silent. That reasoning was right, and the resolver and the path guard took the field anyway. Three entries answered one question two ways, which is how the hole reopened.

- **One guard now answers that question everywhere.** `.claude/workflows/hooks/entry-point.mjs` exports `isProcessEntryPoint`, and the launcher, the resolver, and the path guard all call it. The guard resolves `process.argv[1]` through `realpathSync` and compares the result with the module's own URL. Both operations predate every Node the floor allows, so the guard needs no version check and no second answer. The floor stays `^22.18.0 || >=23.6.0`, and that range now states something true, because unflagged type stripping is the newest Node feature the gate depends on.

- **The suite grew from 65 cases to 72, and the supported range became part of the evidence.** Three cases drive the guard through a real launch: direct, through a symlinked parent, and as a module the entry merely imports. One case per entry pins that the entry decides through the shared guard alone. One more case runs the real launcher against the real resolver with type stripping switched off, which proves the declared floor blocks rather than permits. Reverting any single entry to `import.meta.main` turns that entry's case red and leaves the other two green. The older builds carry the rest of the proof. The suite ran green on Node 23.11.1, Node 24.1.0, and Node 26.5.0, and the same suite showed 19 failures on the two older builds before the fix. A later run covered Node 22.18.0 and Node 23.6.0, and all 72 cases passed on both.

- **Continuous integration now runs the suite at the declared floor, so the range checks itself.** The suite was never the gap. It named this defect precisely on an in-range build, and a single pinned Node denied it the chance. The `check` job runs `test:workflows` on Node 24, where every feature both defects reached for exists. A `workflow-floor` job now runs the same suite at the floor, and `ci-success` lists it. The declared range is a union of two intervals, so it carries two lower edges, and the job runs both. That distinction does the real work. Node 22.18.0 carries `import.meta.main` and Node 23.6.0 doesn't, so only the second edge turns the silent permit red. Reverting the launcher's guard turns six cases red on 23.6.0 and one on 22.18.0, and that one case reads the source rather than running it.

## The capability the boundary couldn't carry

Six rounds of adversarial review ran over these hooks, and three consecutive rounds reproduced a way through the bound the section above called exact. The maintainer removed the capability that needed the bound rather than attempt a seventh boundary. A record that hides that teaches the next reader to try again, so this section states what went, why, and what the gate stopped promising.

- **The bound was a self-declaration rather than a fact git states.** `git rev-parse --git-common-dir` ran with the candidate directory as its working directory, and git answered from whatever `.git` that directory held. A `.git` file is plain text carrying `gitdir: <path>`, so a single file write made any directory claim membership in this repository. The review reproduced the full path: a planted oxlint plugin ran and left a marker on disk. The claim costs an actor nothing it doesn't already have, because writing a file is the one action this hook exists to answer.

- **The climb depth and the climbing path fell out of step under a symlink.** The depth came from git, measured against git's resolved path, and the walk applied that count to the caller's unresolved path. One symlinked component made the two disagree. Overshoot climbed past the repository root, undershoot stopped early and permitted in silence, and the review reproduced both, one of them with code execution. The claim that no symlink widens the bound read the comparison and never read the arithmetic beside it.

- **Every probe failure collapsed into the same answer as "outside the repository."** An old git, a git missing from the path, a refusal over dubious ownership, or an inherited `GIT_DIR` each returned a non-zero status, and the caller read that as "no directory is reachable." The gate then went quiet, which is the worst failure this design has. The review reproduced it by reducing `PATH`.

- **The new rule is blunt on purpose: each hook serves only the checkout it lives in.** The gate names its own checkout's `probity.config.ts`, always, and runs with its own checkout as the working directory. No walking, no probing, and no foreign configuration loaded. The formatter names its own checkout's `.oxlintrc.json` and `.oxfmtrc.json` and starts its own `oxlint` and `oxfmt`, always, and skips an edited path that resolves outside its checkout instead of linting it. The skip is the load-bearing half. Linting a foreign path is what sent the linter up the tree after a foreign configuration in the first place.

- **The containment check is a resolved-prefix comparison, and it defends nothing.** The formatter resolves symlinks on the edited path and on its own checkout root, then asks whether the first sits under the second. Inside, the hook judges the file under its own configuration. Outside, it does nothing at all. Neither branch reads, loads, or runs anything from outside the checkout, so an actor who defeats the check wins either a skipped file or a file judged under this repository's own rules. Both outcomes are safe, which is why the simplest correct check is the right one here and why it needs no resistance to an adversary. The old check had to be exact because getting it wrong started a foreign program.

- **What the gate covers, stated plainly.** It covers an edit whose path resolves inside the session's own checkout, for the orchestrating session and for every subagent under it. The word resolves is load-bearing, and the section below records the round where it wasn't yet true. It doesn't cover an edit a subagent makes inside another worktree. That edit still reaches the gate, the gate still reads this checkout's allow list, the foreign path matches no rule, and the edit proceeds with no verdict. The implementation phase runs one implementer per cluster in its own worktree, so this is the ordinary case rather than an edge case. The way to gate a worktree is to run a session rooted in that worktree, which needs that worktree's own install and its own committed `probity.config.ts`. The earlier claim that a worktree needs no install described a capability this repository no longer has.

- **The modules that existed only for the old answer went with it.** `.claude/workflows/hooks/repository-scope.mts` held the bound and `.claude/workflows/hooks/configuration-scope.mts` held the walk over it. This change deletes both, along with the bound's own specification. `.claude/workflows/hooks/hook-payload.mts` went with them, because it was the seam between two hooks that no longer ask the same question, and the formatter is now the only reader of an edited path.

- **The suite shrank from 72 cases to 57, and the promise shrank with it.** The cases that went pinned a boundary this repository no longer draws: the bound's own unit specifications, the gate configuration a worktree edit selects, and the formatter's behavior inside a checkout it doesn't own. A smaller suite pinning a smaller promise is the outcome here, not a regression. Four deliberate breakages stood behind what remained, each measured against that 57-case suite. Dropping the containment check turned three cases red. Reintroducing the formatter's walk turned six red, the planted plugin among them. Reintroducing the gate's walk turned two red on a faithful revert, and three when the walk climbed unbounded, so the four this record first printed was wrong on both readings. Inverting the containment check, so the formatter skips every path, turned five red. Each run broke a scratch copy and then restored it, because three implementers before this one shipped a first draft whose specification couldn't fail.

## The defect the simplification introduced

The blunt rule above pinned each hook to its own checkout, and the gate's half of it compared two paths that live in different spaces. Both reviewer seats reproduced the same silent permit independently, so this section names it too.

- **The gate matched a resolved glob against an unresolved path, so one aliased component turned it off.** The resolver names its own `probity.config.ts` through `import.meta.url`, and Node resolves symlinks there, so the configuration's directory is physical. The gate anchors a block's `files` globs to that directory, so the globs are physical too. Its Claude Code adapter then builds the action path as `path.resolve(payload.cwd, tool_input.file_path)`, which expands `.` and `..` and resolves no symlink. Scope came down to a string comparison across two spaces. One aliased component anywhere in the checkout's path made every in-scope edit match no rule, so the gate allowed, the hook exited 0 with empty standard output, and Claude Code read that as no opinion. Every implementation edit in such a session landed unjudged with nothing on either stream, which is the worst failure this design has. The trigger is ordinary rather than exotic. macOS aliases `/tmp` onto `/private/tmp`, a convenience alias pointing at another volume does it, and a Fedora Atomic host points `/home` at `/var/home`. A run against the real binary, with a deterministic rule and byte-identical writes, reproduced both ends: the physical path answered with a deny decision, and the aliased path exited 0 with both streams empty.

- **The fix moves the payload's path into the space the configuration already occupies.** The resolver now resolves the action path through `realpathSync` before it hands the payload to the gate. Resolving the payload is the only direction that works. A resolved path is canonical while an alias isn't, since a checkout answers to any number of aliased names and un-resolving the configuration's directory would have to pick one of them. The configuration's directory can't be un-resolved either without reading `process.argv[1]`, the unresolved-path idiom the entry-guard section above removed for the same reason. The sibling formatter hook already resolved both sides of its own comparison, so the two hooks stated opposite answers about one file until now, and the disagreement landed on the permit side.

- **A path whose last component doesn't exist yet still resolves.** A `Write` payload names a file that need not exist, and `realpathSync` throws on it. The resolver walks up to the longest ancestor that does exist, resolves that, and rejoins the missing tail, so a write into a directory the tool is about to create resolves the same way. `notebook_path` takes the same treatment as `file_path`, because `NotebookEdit` sits in the same matcher and would otherwise keep the defect alive in a corner of it.

- **The suite grew from 57 cases to 61, and every property has a case that fails without it.** Two cases drive the real gate binary against a deterministic rule through an aliased prefix, one for an edit and one for a notebook, and both read the verdict rather than an argument string. That distinction matters here, because the gate-scope cases that predate them assert only the `--config` argument, which is now a constant, so they pin almost nothing on their own. Handing the gate the payload's path unresolved turns those two red. Two further cases pin the formatter's containment check in both directions: a path outside the checkout that resolves inside it gets judged, and a path inside the checkout that resolves outside it gets skipped. Replacing that check's resolved comparison with a plain one turns exactly those two red, where the same edit left all eighteen format-hook cases green before this round. Dropping the containment check outright now turns four red rather than three, and making the formatter skip every path turns six rather than five. The two walk figures keep the counts recorded above, because reintroducing a walk to re-measure them is the one thing this design won't do again.

## Alternatives

- **Staying on `tdd-guard`**: rejected. The storage model fails under parallel worktrees, and its own README steers new projects to the successor.
- **The upstream plugin, alone or alongside the pin**: rejected. Its hook runs the package unpinned in a hot path, and a plugin update can restore that hook with no signal.
- **Guarding everything and excluding by exception**: rejected. The exception list is the failure mode the predecessor demonstrated, and the worktree trap proved it live.
- **Confining the resolved checkout and still running its program**: rejected. It leaves the executable choice on the edited path, so the whole defense rests on the confinement being exactly right. Pinning the program keeps a foreign binary out of reach even when the bound has a bug, and it costs a worktree install rather than buying one.
- **A seventh attempt at a safe cross-checkout bound**: rejected. Three consecutive rounds reproduced a defect in the same code, twice with execution, and each fix moved the hole rather than closing it. The capability was worth less than the boundary cost, so it went instead.
- **Gating a foreign worktree by loading its configuration read-only**: rejected. `probity.config.ts` is a TypeScript module the gate imports and `.oxlintrc.json` names JavaScript plugins the linter loads, so no read of either is passive. Reading a foreign configuration is the execution path, not a step before it.
- **The upstream matcher verbatim, shell commands included**: deferred. The latency tax across a shell-heavy repository outweighs the drift risk today, and the widening stays the named upgrade.
- **Waiting for upstream to resolve the subagent record itself**: rejected. The upstream tracker never mentions subagents, and the pipeline needs the gate now. One top-level session per worktree, or serial clusters, would each trade a working dispatch model for twelve lines of derivation.
- **An automated spec over the gate's verdict**: rejected. It would spend a model call per run and return a soft answer, so the recorded probe is the honest check.
- **Chain verification for the review marker now**: deferred. The convention alone cuts the re-review cost, and ADR-0039's trust model already owns the boundary.

## Consequences

**Good**: an implementation edit with no failing test in the acting session meets a blocked tool call. That holds in the orchestrating session and in every subagent under it, for a file inside the session's own checkout. The gate carries no shared state, so parallel worktree clusters never answer for each other. The scope keeps documents, specifications, configuration, and tooling editable, and writing a test never blocks. A fix push pays for an incremental review pass instead of a whole-branch one. Rollback is one hook entry.

**Bad, and accepted**: each in-scope edit that misses the fast path spends a model call, and the allow list is the only cost control. The verdict is probabilistic, so the deterministic gates stay the proof of discipline. The resolver rests on a path convention the harness never documented, with the fallback and the probe as the containment. A broken gate fails closed and stops every edit until the maintainer intervenes. Shell-driven writes skip the gate. An edit a subagent makes inside another worktree isn't gated at all, and gating it means running a session rooted in that worktree, with that worktree's own install. The formatter skips such an edit too, so a foreign worktree gets no formatting and no linting from this checkout's hook. The pin carries three vendor software development kits for the one the gate invokes.
